# 📘 Final Notes: Docker Compose + Redis + Flask Integration

## 1. Basic `docker-compose.yml`

```yaml id="z7kq1a"
version: "3.0"

services:
  web:
    build: .
    ports:
      - "8000:5000" => PORT MAPPING to access application container from its port= 5000 on which the application is running within the container by our local device on its port = 8000

  redis:
    image: redis
```

* We can also do PORT MAPPING in docker-compose.yml Files as shown above.

* In docker-compose.yml files -: INDENTATION MATTERS. So; DO PROPER INDENTATION like we do in Python Files.

---

## 📘 Final Note (Updated)

```yaml
services:
  web:
    build: .
    image: web-app
    ports:
      - "8000:5000"

  redis: 
    image: redis
```

---

## 🔍 For Redis

👉 **No port mapping is done for Redis**

* You did **NOT write `ports:`**
* So Redis is **not exposed to your host machine**

---

## 🧠 What happens

* Redis is available only **inside Docker network**
* Containers communicate internally using service names

```python
host='redis'
```

---

## 🔌 Access behavior

| From where               | Access | How            |
| ------------------------ | ------ | -------------- |
| Inside container (`web`) | ✅ Yes  | `host='redis'` |
| From your laptop         | ❌ No   | Not exposed    |

---

## ⚠️ Important Point (Added)

👉 **If no port mapping is done:**

* Only **internal container-to-container communication** works ✅
* Docker handles communication using its **internal network**
* No access from outside (host machine) ❌

---

## ⚡ Final Idea

👉 No `ports` = only internal Docker communication with these containers and container to container communication within their internal Private network
👉 Port mapping needed only for external access 🚀


## 2. What this setup means

* **web service** → your Flask application (application container)
* **redis service** → Redis database container
* Docker Compose:

  * Creates a **shared network**
  * Runs all services together
  * Enables communication using **service names**

---

## 3. `services` (Core Concept)

* Defines all containers in the application
* Each service = one container
* Service names are **user-defined** but must be used for communication

Example:

```yaml id="r9v8k2"
services:
  web:
  redis:
```

---

## 4. Application Container vs Other Services

### ✅ Application Container

* The service that contains your application code
* Usually the one using:

```yaml id="m3k2q1"
build: .
```

👉 In this case:

```yaml id="k8w2n9"
web:
  build: .
```

* This means:

  * Docker builds an image using your **Dockerfile**
  * Runs your Flask app inside this container
  * build key name indicates that this container / image is created from the local Dockerfile which is present in the directory of your application folder
 
👉 So:

* `web` = **application container** .i.e. name of the service for application container

---

### 🔹 Other Services (e.g., Redis)

```yaml id="v1n4t5"
redis:
  image: redis
```

* Uses a prebuilt image from Docker Hub
* No Dockerfile required
* Acts as a **dependency/service container**

---

## 5. `build: .` (Important Explanation)

```yaml id="b3x9l7"
web:
  build: .
```

* Tells Docker Compose to:

  * Build an image from a **Dockerfile in the current directory**
* `.` means:

  * Current folder where `docker-compose.yml` exists

👉 Used when:

* You have your own application code (Flask app)

---

## 6. Service Name = Hostname (Very Important)

Service names act as **hostnames inside Docker network**

| Service Name | Acts As         |
| ------------ | --------------- |
| `web`        | web container   |
| `redis`      | redis container |

👉 Inside containers:

```python id="x2k9q8"
host='redis'
```

means:

> Connect to the container named `redis`

---

## 7. Flask Redis Connection

```python id="c8m1p4"
import redis

cache = redis.Redis(host='redis', port=6379)
```

### Why this works:

* Docker provides **internal DNS**
* `redis` resolves automatically to the Redis container

---

## 8. Communication Flow (Inside Docker)

```id="f7g2h9"
[ web container (Flask app) ]
          |
          | host = "redis"
          ↓
[ redis container ]
```

* Containers communicate using service names
* No IP address needed
* Docker handles name → IP resolution internally

---

## 9. Port Concept

Redis default port:

```id="p5l8r2"
6379
```

* Inside Docker → used automatically
* To access from host machine → expose port:

```yaml id="q2m7x3"
ports:
  - "6379:6379"
```

---

## 10. When It Works vs Fails

### ✅ Works (Inside Docker)

```bash id="d8k3v1"
docker-compose up
```

* Both `web` and `redis` run in containers
* Internal DNS resolves `redis`
* Flask connects successfully

---

### ❌ Does NOT Work (Outside Docker)

```bash id="n4s7t2"
python app.py
```

* Running on your local machine
* Your OS does NOT know hostname `redis`
* DNS resolution fails → connection error

---

## 11. Why It Fails Outside Docker

* `redis` is not a real domain/hostname on your system
* It exists only inside Docker’s internal network
* Outside Docker:

  * No service discovery
  * No internal DNS
  * No container network

---

## 12. If Running Flask Locally (No Docker)

Use:

```python id="y3t6k9"
cache = redis.Redis(host='localhost', port=6379)
```

And ensure:

* Redis is installed and running locally
* Port 6379 is accessible

## 13. How Service Names Should Be Used in Python

* The `host` value must match the **service name in docker-compose.yml**

Example:

```yaml id="h2j8k4"

  redis:
```

```python id="u9p1a6"
host='redis'
```

If renamed:

```yaml id="s5d2n8"

  cache:
```

Then:

```python id="r6w3t1"
host='cache'
```

## 14. Key Rules

* Service name = hostname inside Docker
* Application container = service using `build`
* Other services = dependencies using `image`
* Communication inside Docker uses service names
* Outside Docker requires `localhost` or IP
* Redis default port = `6379`

## 15. Golden Rule

👉 **Service name in `docker-compose.yml` must match the hostname used in your application code**

## 16. Final Idea

👉 `docker-compose.yml` is a **blueprint** that:

* Builds containers (`build`)
* Pulls images (`image`)
* Connects services via a shared network
* Enables inter-container communication using service names instead of IPs 🚀


**generally, image names must refer to images available on Docker Hub (or another registry)** in docker-compose.yml, but there are a few important details:

---

## ✅ 1. When you use `image:` in `docker-compose.yml`

```yaml
redis:
  image: redis
```

* Docker will try to pull the image from **Docker Hub**
* `redis` here refers to the official Redis image on Docker Hub

👉 Equivalent to:

```
docker pull redis:latest
```

---

## ✅ 2. Image name format

Images usually follow this structure:

```
[repository]:[tag]
```

Examples:

```yaml
image: redis:latest
image: nginx:1.25
image: python:3.11
```

* If tag is not specified → defaults to `latest`

---

## ✅ 3. Custom images (local build)

If you build your own image using:

```yaml
web:
  build: .
```

* Docker builds the image locally from your Dockerfile
* You are **not required to have it on Docker Hub**

You *can* optionally name it:

```yaml
web:
  build: .
  image: myapp:1.0
```

* This tags your local image as `myapp:1.0`

* If you did not give image name to your application container via "image:" then DOCKER will give a random image name to it.

---

## ⚠️ 4. If image is NOT available on Docker Hub

* Docker will fail with an error like:

  ```
  pull access denied or repository not found
  ```
* Unless:

  * The image exists locally
  * Or you provide a valid registry path

---

## 🌐 5. Private / other registries

Images can also come from:

* Docker Hub
* Private registries
* Cloud registries (AWS ECR, GCP, Azure)

Example:

```yaml
image: myregistry.com/myapp:1.0
```

---

## 🧠 Summary

* ✔ `image:` → must exist on Docker Hub (or another registry)-: if not found then DOCKER will give ERROR by saying unable to pull image from DockerHub.
* ✔ If not found locally, Docker tries to pull it
* ✔ `build:` → builds image locally (no Docker Hub needed)
* ✔ You can optionally tag built images from your local Dockerfile using `image:`

---

👉 **Simple rule:**

* `image:` → pull existing image from docker hub.
* `build:` → create your own image locally

Here’s the **clear difference** between the two:

---

# 🚀 `docker compose up`

* Starts containers using **existing images**
* If images are already built → uses them directly
* If not built yet → Docker will build only if needed (based on config), but usually expects images to exist or build cache

👉 Does **not force rebuild** every time

---

# 🔨 `docker compose up --build`

* **Forces Docker to rebuild images** before starting containers
* Rebuilds images defined with:

  ```yaml
  build: .
  ```
* Ignores cache and ensures latest code is included

👉 Always rebuilds application image

---

# 🧠 Key Difference

| Command                     | Behavior                       |
| --------------------------- | ------------------------------ |
| `docker compose up`         | Uses existing images (fast)    |
| `docker compose up --build` | Rebuilds images before running |

---

# 📌 When to use what

### Use `docker compose up` when:

* No code changes
* Images already built
* Just starting/stopping containers

### Use `docker compose up --build` when:

* You changed:

  * Dockerfile
  * Application code
  * Dependencies (`requirements.txt`)
* You want latest changes reflected

---

# ⚡ Simple analogy

* `docker compose up` → “Run what already exists”
* `docker compose up --build` → “Recreate everything fresh, then run”

---

* if u want to recreate everything without using "docker compose up --build" then remove all the images which were created by "docker compose up" command and then re-apply the command-: "docker compose up" -: this will also result in recreation of all the containers / images from scratch.


* Also "docker-compose.yml" should be named like this only in your application folder no random names are allowed 

* Also "Dockerfile" should be named like this only in your application folder no random names are allowed

## 📘 Difference: `docker compose up` vs `docker compose start`

---

## 🚀 `docker compose up`

* Creates **and starts** containers
* Builds images (if needed)
* Creates network
* Runs everything from scratch if not already created

👉 Used for **first time run or fresh setup**

---

## ▶️ `docker compose start`

* Starts **already created containers**
* Does **NOT build images**
* Does **NOT create new containers**

👉 Used after:

```bash
docker compose stop
```

---

## 🧠 Key Difference

| Feature            | `up` | `start` |
| ------------------ | ---- | ------- |
| Creates containers | ✅    | ❌       |
| Builds images      | ✅    | ❌       |
| Starts containers  | ✅    | ✅       |
| Used first time    | ✅    | ❌       |

---

## 🔄 Flow Example

```text id="rgubxq"
docker compose up
    ↓
Containers created + running

docker compose stop
    ↓
Containers stopped

docker compose start
    ↓
Same containers started again
```

---

## ⚡ Final Idea

* `up` → create + build + run
* `start` → just run existing containers

👉 Use `up` first, then `start` after stopping 🚀


Here’s the **clear difference** between `docker compose stop` and `docker compose down`:

---

# ⏹️ `docker compose stop`

* Stops running containers **but does NOT remove them**
* Containers still exist (just in stopped state)
* Can be restarted later quickly

### What remains:

* Containers ✅
* Networks ✅
* Volumes ❌ (not affected)

### Restart later:

```bash
docker compose start
```

---

# 🧹 `docker compose down`

* Stops **and removes containers**
* Also removes:

  * Containers ❌
  * Networks ❌
* Volumes are **NOT removed by default**

### Optional:

```bash
docker compose down -v
```

* Removes volumes too ❌ (data deleted)

---

# 🧠 Key Differences

| Feature            | `stop` | `down`            |
| ------------------ | ------ | ----------------- |
| Stops containers   | ✅      | ✅                 |
| Removes containers | ❌      | ✅                 |
| Removes networks   | ❌      | ✅                 |
| Removes volumes    | ❌      | ❌ (unless `-v`)   |
| Can restart easily | ✅      | ❌ (must recreate) |

---

# 📌 When to use what

### Use `stop` when:

* You want to pause containers temporarily
* You plan to resume later

```bash
docker compose stop
docker compose start
```

---

### Use `down` when:

* You want to clean everything
* You want to reset the environment
* You are done with the setup

```bash
docker compose down
```

---

# ⚡ Simple analogy

* `stop` → pause the containers
* `down` → delete the setup
