A **Distributed Version Control System (DVCS)** is a setup where every user has a full copy of the project’s entire history on their local machine, rather than relying on a single central server. This allows you to work offline, branch code quickly, and ensures that if the main server fails, any user's local copy can restore the project.

**Open source** refers to software with source code that anyone can inspect, modify, and enhance because its design is publicly accessible. This collaborative model encourages transparency and community-driven innovation, allowing users to fix bugs or add features freely.

### **Git Init Command**

* **What it does:**
    Initializes a new, empty **Git repository** in the current directory, turning a standard folder into a project that can track changes.
* **What it creates:**
    * A hidden folder named **.git**.
    * This folder contains all the necessary metadata, object databases, and configuration files for version control.
* **Key Point:**
    You only run this **once** per project to start tracking its history.

The `.git` folder is a **database** that stores the entire history, configuration, and branching information of your project. It is technically a directory (folder), though it functions as the "brain" of your repository and it is created on command-: "git init"

### What it Contains
* **Objects:** Every version of every file you've ever saved (commits).
* **Refs:** Pointers to your branches (like `main`) and tags.
* **Config:** Your project-specific settings (like the remote URL for GitHub).
* **HEAD:** A file that keeps track of which branch you are currently working on.



### Why it is Hidden
It is hidden (starting with a `.`) to protect it from **accidental deletion or modification**. If you manually change or delete files inside this folder, you could corrupt your entire project history or lose the ability to track changes.

### Why it isn't "Pushed"
You don't push the `.git` folder because the GitHub server **already has its own version** of it. When you run `git push`, you are sending the *data* inside your `.git` folder to update the one on the server, rather than uploading the folder itself as a file.

It is **by default** never pushed and does **not** need to be written in your `.gitignore` file. Git is designed to recognize its own internal "brain" and automatically excludes it from being tracked as a file within the project.



### Why it stays local:
* **Automatic Exclusion:** Git treats the `.git` folder as the repository itself, not as "content" to be versioned.
* **Redundancy:** When you push, Git sends the *compressed data* (commits, blobs, and trees) stored inside that folder to the server's own `.git` directory.
* **Safety:** If you were to track the `.git` folder inside itself, you would create an infinite loop of data.

You only use `.gitignore` for files you **created** (like `node_modules`, `.env` secrets, or temporary build files) that you want Git to ignore.

* Git Push Command

What it does: Uploads your local repository commits (the "save points" on your computer) to a remote repository (like GitHub).

Common Usage:

• `git push <remote> <branch>`: Sends changes from a specific local branch to a specific remote.

• `git push origin main`: The most common command; sends your `main` branch changes to the `origin` remote on GitHub.

• `git push -u origin main`: Uploads your changes and sets the "upstream" tracking, so in the future, you can just type `git push`.

• `git push --force`: Overwrites the remote history with your local history (use with extreme caution!).

Important Note: Before you can `push`, you must have committed your changes locally. You cannot push "staged" files that haven't been committed yet.

Key Concept: Pushing is like "uploading" or "syncing" your work to the cloud so your team can see it and you have a backup.
Which local branch gets pushed?

By default, `git push origin main` pushes code from your current local branch to the `main` branch on GitHub.

1. If you are on the local main branch: It takes your local `main` commits and sends them to the GitHub `main`. This is the standard, safest way to work.

2. If you are on a different local branch (e.g., feature-login): If you run `git push origin main`, Git will try to push code from `feature-login` into the remote `main`.

• The Danger: You might accidentally overwrite "perfect" code with "work-in-progress" code.

The "Safe" Golden Rule: Always match your names. If you are on a local branch called `dev`, push it to a branch called `dev` on GITHUB:

• Correct way: `git push origin dev`

• Shortcut: Use `git push` (if you used the `-u` flag earlier).

How to check where you are standing: Run `git branch`. The one with the asterisk (*) and the green color is your current local branch and by using "git push" command "git" will try to push current local branch which is already commited to the specified "remote branch"(GITHUB BRANCH) in `git push` command

* Git Restore Command
What it does: Helps you undo changes in your working directory or unstage files. It is the modern, safer way to "discard" changes you haven't committed yet.

Common Usage:

• `git restore <file>`: Discards local changes in a file and restores it to the last committed state. (The "Undo" button for your code).

• `git restore --staged <file>`: Unstages a file (removes it from the `git add` area) but keeps your actual code changes intact.

• `git restore .`: Discards all local changes in the current directory.

Key Concept: `git restore` is specifically for your working tree (files you are editing) and the index (staged files). It does not delete your commit history; it just cleans up your current workspace.

Important Warning: Running `git restore <file>` will permanently delete any uncommitted changes in that file. There is no "undo" for this action!
Real-World Example: Resetting to "Pushed" Status

Imagine you have already pushed your project to GitHub, and your local workspace is clean.

1. The Change: You open `script.py` and delete 10 lines of code by mistake.

2. The Status: You run `git status`. It shows:

  • `modified: script.py`

  • (Changes not staged for commit).

3. The Action: You want to go back to exactly how the file looked when you last committed.

  • Command: `git restore script.py`

4. The Result: Your deleted lines are back! If you run `git status` again, it shows:

  • `nothing to commit, working tree clean`

  • Your local file now perfectly matches the "Pushed" status on GitHub.
CRITICAL CLARIFICATION: Commit vs. Push

• Restores From: Your most recent local COMMIT (the last time you ran `git commit`).

• Does NOT Restore From: Your last PUSH on GitHub.

Key Takeaway:
 `git restore` uses your local `.git` folder and does not need the internet. It resets your file to the last "save point" .i.e. last(latest) COMMIT you created on your own computer, even if you haven't sent those changes to GitHub yet.

* Git Clone Command

What it does: Creates a complete copy of an existing remote repository (from GitHub) and downloads it to your local computer. It’s like downloading a project folder, but it also includes the entire history of the project.

Common Usage:

• git clone <url>: Downloads the repository into a folder named after the project (.i.e. repo-name in GITHUB) in cwd.

• git clone <url> <folder-name>: Downloads the repository into a specific folder name of your choice. 

Key Concept: When you `clone`, Git automatically:

1. Creates a new folder for you.

2. Initializes it as a Git repository.

3. Sets up a remote named origin  pointing to the GitHub URL.

4. Downloads all files and the entire commit history.

Important Note: You only need to run `clone` once per project. After that, you use `git pull` to get new updates.

Clone vs. Download ZIP: Unlike "Download ZIP" on GitHub, `git clone` keeps the connection to the remote server, allowing you to push and pull changes later.
CRITICAL DIFFERENCE: Clone vs. Download ZIP

• Download ZIP: This is a "one-time" snapshot. It will NOT keep the connection to the remote origin or branches. It is a completely independent folder with no Git history. You cannot `push` or `pull` from it.

• Git Clone: This keeps a permanent connection to the remote server. Because it preserves the link to the origin and all branches, it allows you to `push` your changes back to GitHub and `pull` new updates later.
Can you clone without a URL?

Rule: You always need a source to clone from. Git must know what it is copying.

• Remote: Use a URL (GitHub/GitLab).

• Local: Use a file path (another folder on your PC).

  • Example: `git clone /path/to/old-folder new-folder` (No internet needed!)

Note: If you type `git clone` by itself, Git will show an error: fatal: You must specify a repository to clone.
Important Requirement for Local Cloning: When cloning from a local path (e.g., `git clone /path/to/old-folder`), the old-folder MUST already be a Git repository (meaning it must have been initialized with `git init` or previously cloned). You cannot "clone" a regular folder that doesn't have a `.git` history.
Does clone create a new folder?

• Standard Behavior: Yes, Git always tries to create a new folder.

• If the folder already exists: Git will NOT overwrite it. Instead, it will give you an error: `fatal: destination path 'folder-name' already exists and is not an empty directory.`

• Cloning into an existing folder: You can only clone into an existing folder if that folder is completely empty. Even then, Git will not "overwrite" files; it will simply place the repository inside that empty space.

Key Takeaway: Git protects your data by refusing to clone into a folder that already contains files.
Is the remote name always 'origin'?

• Default Behavior: Yes, by default, `git clone` automatically names the connection to the remote repository "origin".

• Can you change it? Yes. If you want a different name (like "github" or "source"), you can use the `-o` or `--origin` flag during cloning.

  • Example: `git clone -o github `

  • This will name the remote "github" instead of the default "origin".

Key Takeaway: While "origin" is the industry standard and Git's default, it is just a nickname. You can customize it if needed.
Cloning into an existing folder

• The Rule: You can clone into an existing folder ONLY if it is completely empty.

• The Error: If there is even one file (like a `README.txt` or a hidden file) in that folder, Git will stop and say: `fatal: destination path 'folder-name' already exists and is not an empty directory.`

• How to do it: 
To clone into your current empty folder/directory, use a dot: `git clone  .`

Summary: If the folder has any content, Git will refuse to clone there to prevent overwriting your existing work.

## **Git Push Credentials: The Complete Breakdown**

### **Does `git push` always ask for a password?**
**No.** While Git *always* needs to verify your identity to let you upload code, it does not always ask you to type it in.

---

### **1. When will it ASK?**
It will ask for your credentials in these specific cases:
* **First time:** When you are pushing to a new GitHub account on a fresh computer.
* **Credentials Expired:** If your login "token" has timed out or been revoked.
* **No Helper:** If your computer isn't set up to "remember" logins (no Credential Manager).
* **Manual Login:** If you are using a Personal Access Token (PAT) and haven't saved it yet.

---

### **2. When it ASKS: What do I enter?**
If the terminal prompts you for a "Password," **do not enter your GitHub website password.** GitHub disabled this in 2021 for security. Instead:

* **The Browser Pop-up (Recommended):** Most modern Git installs will open a window. Click **"Sign in with your browser."** You just click "Authorize" in your browser tab, and you are done.
* **Personal Access Token (PAT):** If the terminal asks for a password and no window pops up, you must enter a **PAT**.
    * **To get one:** GitHub Settings → Developer Settings → Personal Access Tokens → Tokens (classic) → Generate New Token.
    * **To use it:** Copy the long code and paste it into the terminal when it asks for your "Password." (Note: The terminal won't show characters while you paste/type for security).


    ### **3. When will it NOT ask? (The GCM / Manager)**
It will **not** ask if your computer is using a **Credential Helper**.
* **The "Manager":** If you run `git config --get credential.helper` and it says `manager`, your computer is using **Git Credential Manager (GCM)**.
* **The Vault:** GCM saves your GitHub "ID badge" (token) inside the **Windows Credential Manager** (a secure vault on your PC).
* **Automatic Handshake:** Every time you `push`, GCM automatically grabs that badge from the vault and shows it to GitHub. It happens in the background so you never see a password prompt.

ex-:
(base) C:\Users\Omkar Raut\Desktop\DataScience-Learning-Journey>git config --get credential.helper
manager

### **4. `git config` vs. Credentials (The Big Difference)**
It is easy to confuse these two, but they do completely different things:

| Feature | `git config user.name` | **Git Credentials** |
| :--- | :--- | :--- |
| **Purpose** | **Identity (The Signature)** | **Security (The Key)** |
| **Analogy** | Signing your name at the bottom of a letter. | Using a key to unlock the post office box. |
| **Effect** | Tells GitHub whose name to show in history. | Proves you have permission to upload code. |
| **Requirement** | Does **NOT** need a password. | Requires a **PAT** or **Browser Login**. |

### **5. How to ACCESS/Find your "Saved" Password on Windows**
If Git isn't asking you for a password and you want to see where it's stored or delete it (e.g., to switch accounts):

1.  Open the **Windows Start Menu**.
2.  Search for **"Credential Manager"** and open it.
3.  Click on the **Windows Credentials** tab.
4.  Scroll down to the **Generic Credentials** section.
5.  Look for an entry named **`git:https://github.com`**.
6.  Click the arrow to expand it. You can see the user name and **Remove** or **Edit** the saved token/password there.
